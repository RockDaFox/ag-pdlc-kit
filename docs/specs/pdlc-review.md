# Spec — pdlc-review

> **Status: Draft** — the review of a spec (decisions 12 to 16) is authorised and not yet built. The review of code, decisions 1 to 11, is shipped.
>
> Living document: any change to the `pdlc-review` skill is reflected here in the same change. Revised 2026-10-15.

## Summary

The target is code or a spec, and the user says which. Code is read as described next. A spec is read by two fresh agents, one as a business analyst and one as a tech lead, and their findings are shown together without merging, none dropped.

`pdlc-review` reads a diff and reports what an experienced tech lead would raise on it: code quality, respect of the repository's conventions, correct use of the libraries it leans on, and whether the result is readable and maintainable by a human. Conformance to the spec that authorised the work, tests included, is one axis of that review, not the whole of it. It reports graded findings, asks which ones to apply, applies only those, then runs the repository's own checks to confirm the corrections broke nothing.

It is the second skill of the kit's second family: the other three record what is decided, [`pdlc-build`](pdlc-build.md) carries out the work a record authorises, and this one holds the result to a standard before it is committed. It closes that skill's last known gap — "no handoff to a review step, because no review skill exists" — and gives the evidence block a consumer inside the kit.

What makes it a kit skill rather than one more generic reviewer is that it reviews against things the repository has written down, not against a checklist it carries: the code style zone of `AGENTS.md` for the conventions, `{docs_root}/specs/<feature>.md` for the scope the work was authorised against, and the dependency versions actually present in the tree for how a library is meant to be used. Tech-lead judgement applies where none of them settles the question. This closes a chain the kit already half-had: `pdlc-init` writes the conventions down, and this skill holds the code to them.

The skill runs no command of its own: decision 8 sends every correction into the build loop instead, which is where execution already lives. [ADR-0015](../adr/0015-review-corrections-enter-the-build-loop.md) records that, and supersedes [ADR-0014](../adr/0014-a-skill-may-run-discovered-repository-commands.md) only because that record named the loop's callers inside its Decision — the grant itself is carried forward unchanged.

## Non-goals

- Reviewing a spec does not run the build loop and does not change code.
- `pdlc-feature` does not start the review by itself. After it writes a spec it asks whether to launch one, and the user can skip, as [pdlc-feature](pdlc-feature.md) decision 18 states. The review stays on demand, as decision 1 states.
- Spec review is not a second skill. It is another target of this one.
- Neither lens judges whether the feature should exist. The user settled that before the spec was written.
- The two lenses do not exchange findings. Each reports on its own.
- The review does not approve, reject or rank a spec or a change. It recommends, and the user decides.

## Decisions

1. **It is a skill invoked on demand, not a step inside the build loop.** A tech-lead review carries its own method — what to read, in what order, what to raise and above all what to let go — which is more than a paragraph appended to [`build-loop.md`](../../skills/_pdlc-shared/build-loop.md) can hold. On demand also keeps it usable on a diff no `pdlc-build` produced: a branch from another session, a colleague's work, a change made by hand. Wiring it into the loop would run it on every build, which is the blocking pre-commit check `docs/PRODUCT.md` §5 rules out in spirit even where it is not literally a hook. The dependency runs the other way instead, and decision 8 is where: the review is not a step of the loop, it is a caller of it.
2. **It reviews against what the repository has written down, not against a shipped checklist.** The conventions come from the code style zone of `AGENTS.md` and from what the surrounding code actually does. A bundled quality checklist would be an invented example that rots and that contradicts the host repository the day the two disagree — the same reason `pdlc-build` ships no per-stack command table. Where the repository has written nothing down, the review says so and falls back to the surrounding code, rather than refusing to run.
3. **Spec conformance is one axis, not the review.** The spec answers two questions no style guide can: does the diff go beyond what was authorised, and does every line of its Behavior section have a test that asserts the result the line states. Where no spec governs the diff, that axis is skipped and stated as skipped — the skill never reconstructs a contract from the code in order to have something to compare against, which is the mechanism that produces a plausible invented record. The tests are read in full, and the build's evidence block is not taken for their description: it is the account of the agent that wrote them, which is the self-judgement [ADR-0017](../adr/0017-a-spec-states-its-behavior-as-testable-lines.md) leaves open and this is the only reading of the tests made by someone else. A test asserting a call or a mock's own answer, a test citing no line, a found test inside the non-goals and a result the spec leaves open that was decided instead of reported are all findings. A spec with no Behavior section gives the tests nothing to be held to, and the review says so.
4. **Library use is reviewed against the version actually in the tree, never against the model's memory of the API.** Standard library and third party alike: a call is judged on the signature, the contract and the idiom the installed version documents — read from the dependency manifest and lockfile, then from the installed source, type definitions or docstrings the repository already carries, and from the library's published documentation for that version where the tree holds nothing readable. This axis is where a review is most dangerous, because a misremembered API produces the most confident wrong finding a model can emit; so every finding of this kind names what it is grounded in, and anything that cannot be grounded is reported as unverified rather than asserted. The finding to look for is not only the call that fails — it is the one that works while ignoring what the library provides: a hand-rolled helper the standard library already has, a deprecated entry point, a resource left unclosed where the documented idiom manages it, an option passed that the installed version silently ignores.
5. **The default target is the uncommitted working tree, and an explicit target is accepted.** Staged and unstaged changes together, because the skill's first use is the moment before a commit. A branch against the trunk, a commit range or a path is accepted as an argument, because the on-demand shape is worth nothing if it only reaches work that has not been committed yet.
6. **Findings are graded — blocking, to fix, detail — and each one is a single line.** The risk this skill carries is noise, not blindness: a model asked to review always finds something to say. The grade forces it to state how much a finding matters instead of listing everything at equal weight, and the one-line budget — location, problem, proposed correction — stops a detail from being argued over a paragraph. A finding that cannot be stated in one line is a finding that needs the user's judgement before anything else, and it is graded accordingly rather than expanded.
7. **It reports first and changes nothing until the user has chosen.** Same shape as [`pdlc-decide`](pdlc-decide.md): the skill reviews, it does not arbitrate. The user answers with the findings they want applied, and only those are applied — no opportunistic cleanup picked up along the way, which would put unreviewed edits in a diff the user believes they scoped.
8. **Every selected correction enters the build loop; none is applied beside it.** A readability correction can break a test, and a review that hands back an unverified tree has moved the problem rather than solved it — but merely re-running the suite would establish only that nothing broke, not that the correction did what it claimed. Routing through [`build-loop.md`](../../skills/_pdlc-shared/build-loop.md) gets both: a correction that changes behavior arrives with a test, and one that changes none says so and leans on the existing suite plus the closing steps. Each correction is a unit of work there, exactly as a behavior is, and the closing steps run once over the set. This skill executes nothing on its own authority, which is what [ADR-0015](../adr/0015-review-corrections-enter-the-build-loop.md) records.
9. **A substantive finding the user declines is recorded in the governing spec's Known gaps.** A declined finding is a decision, and without a trace it resurfaces at every later review — the "settled questions get re-opened" failure the kit exists to prevent. The limit is substance, meaning a finding graded blocking or to fix: a declined detail leaves nothing behind, because a spec padded with every nit somebody waved off is worse than one with a gap in it. Where no spec governs the diff, nothing is written and the skill says so rather than inventing a place to put it.
10. **It commits nothing.** The review ends on a working tree, and the commit stays with whoever owns it — `pdlc-build`'s own ask, `pdlc-feature`'s step 7, or the user directly. Two writers for one commit is the failure that decision 6 of `pdlc-build` already names for records.
11. **The change is read by an agent that did not write it.** The session that built the code and its tests knows what they were meant to say, so it reads that intention into them, and a review made from there is the author's own account of the work. Where the invoking session wrote, discussed or planned the change, it hands the reading to a fresh agent, a subagent where the host offers one, given only the target, the spec path and the review's own instructions: never the evidence block, a summary of the change or the reasons for a choice, since each carries the author's reading across. The agent reads and reports, and edits and runs nothing, so decision 8 and [ADR-0015](../adr/0015-review-corrections-enter-the-build-loop.md) are untouched. The invoking session relays the findings as returned, because the softening this decision removes could come back at the relay: a disagreement is stated beside a finding and never replaces it. Where the host cannot start an agent, the skill says so and asks for a new session, and does not present its own reading as independent. A session with no memory of the change reviews directly. Corrections still enter the build loop in the invoking session, which holds the conversation with the user.
12. **The target is code or a spec, and the user names it.** The default stays the uncommitted working tree, with no exception: [`pdlc-feature`](pdlc-feature.md) names the spec as an explicit target when it launches the review. A spec is a path under `{docs_root}/specs/`, or whatever the user says is a spec. Any other path is code. A path that does not exist, or a file that is not a spec, is a stated error. If the user says "the spec" and several files could match, or none, the skill asks. A range holding both code and spec changes also asks which to review. One entry point serves both, because a second skill would state decision 11 twice and the two copies would drift. The skill's `description` names the spec target, since hosts find the skill from it. `SKILL.md` holds the instructions of each lens as its own delimited block, and the session hands each agent only its own.
13. **A spec is read against what the repository has already decided, not against code conventions.** Each lens has its own sources and its own questions, and each names the sources it lacks, as for code.
    - The business analyst reads the spec, `PRODUCT.md` and the other specs. It asks:
      - Does the spec state what the user sees and can do, with the empty and error states?
      - Is each rule complete, with no case left to guess?
      - Does a word allow two readings?
      - Is a functional decision implied and not written?
      - Does a non-goal contradict a behavior or a decision?
      - Does anything contradict `PRODUCT.md` or another spec, beyond what the spec announces as a change?
    - The tech lead reads the spec, the architecture, the ADRs and the code the spec touches. It finds that code from the spec's prose and from the architecture, because a spec lists no files. The architecture is the Architecture section of `AGENTS.md` and what the code shows. It asks:
      - Can the functional behavior be built in the solution as it stands, or does it need a structural change?
      - Does it fit the architecture and contradict no ADR?
      - Is each Behavior line a result a test can assert from outside?
      - Is a structural decision hidden, or does a decision pass the ADR tests in `decision-records.md` and so call for an ADR?
      - Does the spec disagree with what the code does today, beyond what it announces as a change?

    A spec for new behavior has no code yet. The tech lead then checks it against the structures it would extend, and says so if the spec names none. A difference the spec announces as new behavior, or as the supersession of another decision, is not a finding. The conventions and libraries axes do not apply, and the report says so. A spec with no Behavior section is reported as such, and no lines are written for it, as in decision 3.
14. **Two agents read the spec, each through one lens.** The business analyst stays on the functional side: what the feature does for its user, whether that is complete and clearly worded. It does not judge how the feature is built. The tech lead takes the functional behavior as given and checks that it can be implemented in the solution, which includes the architecture. It does not re-judge the functional choices, and a functional doubt it meets is reported as such. Both are fresh agents, as in decision 11, given the spec path and the instructions of their own lens only. The business analyst reads no code, no ADR and no architecture, so it cannot be led by how the system happens to work. The tech lead reads all three, so it can tell where the spec and the system disagree. The session gives the tech lead the resolved path of `decision-records.md`, because an excerpt of the instructions carries no base directory for a relative link. The lenses ask different questions, so they overlap little. One agent wearing both reads the second lens through the first, and two identical agents find the same points twice. Where the host cannot start agents, a session that wrote or discussed the spec says so and asks for a new session. A session with no memory of the spec reads it under both lenses in turn, and the report says it was a single reader, so the separation of the lenses rests on instruction alone.
15. **The two reports are shown together without merging, and nothing is dropped.** Each finding keeps the line and the grade its lens gave it, tagged with the lens, and the numbering runs on across the two lists. Each agent cites the Behavior line, the decision or the section its finding concerns. A finding that cites the same place as another carries "same place as N", so the match is made on the citation and not on a reading of two sentences. Decision 11 forbids the relay to drop, regrade or soften a finding, and deciding that two findings are one point is a judgement that rewrites them. A place both lenses cite is also the best sign of a real gap.
16. **A correction to a spec does not enter the build loop.** The loop changes code and proves it with a test, and a spec has neither. Each finding carries a kind, given by the agent that reports it: a wording fix, an open question, or another kind such as an ADR to write or a contradiction with another spec. A wording fix is applied to the spec once the user selects it. An open question goes to the user, and the skill does not settle it. Once answered, the answer is written into the spec as a decision, with the rejected options if the user gave them. A finding of another kind is referred and nothing is written: an ADR to [`pdlc-decide`](pdlc-decide.md), a contradiction with another spec to the user. The review edits no file other than the reviewed spec. Decisions 7 and 10 hold: nothing is edited before the answer and nothing is committed. In the [`pdlc-feature`](pdlc-feature.md) flow the draft is not yet committed, so the revised draft is committed at step 5, after the go-ahead on it. A declined finding graded blocking or to fix goes into the reviewed spec's Known gaps, as in decision 9, and so does an open question the user does not answer. The skill proposes the condition and the user can correct it. On a spec, blocking means the lens recommends against approving it in this state, and the decision stays with the user. Decision 8 and [ADR-0015](../adr/0015-review-corrections-enter-the-build-loop.md) are unchanged, because they govern corrections to code. The review closes by stating what was applied, what went to Known gaps and which open questions remain.
17. **The agents recommend and never decide, and the user validates.** A finding is a recommendation, and its grade is the weight the agent recommends, not a gate. No agent approves or rejects a spec or a change, and none declares a finding settled. Where the business analyst and the tech lead diverge, the report shows both at equal weight. Neither is preferred, neither forces its view, and the skill does not break the tie. A functional doubt from the tech lead and a buildability doubt from the business analyst are recommendations of the same standing. The user decides what is applied, declined or ignored, and a spec is approved only by the user's go-ahead. This holds for code as for a spec, and it is what decision 7 means by a skill that reviews and does not arbitrate.

## Behavior

The first ten lines describe the review of code. Lines 11 to 30 describe the review of a spec.

1. Resolve the target: the uncommitted working tree, or the branch, range or path given. If this session wrote, discussed or planned the change, hand steps 2 to 5 to a fresh agent given the target, the spec path and the review's instructions only, and relay what it returns as it is.
2. Read the sources of truth — the code style zone of `AGENTS.md`, the spec governing the change if one exists and the tests the change adds or touches, the dependency manifest and lockfile for the versions in play, and the code around the diff. Name which of them were missing.
3. Read the diff in full, with enough surrounding code to judge it in place rather than as fragments.
4. For every library the diff calls into, establish what the installed version actually provides before judging the call.
5. Report the findings, graded and one line each, numbered so they can be selected, with anything unverified marked as such.
6. Ask which to apply. Nothing is edited before the answer.
7. Read `build-loop.md` — now, not earlier: a review the user closes without selecting anything never needs it.
8. Send each selected finding through that loop as its own unit of work, and nothing else with it. Its closing steps run once over the set.
9. Record the declined substantive findings in the governing spec's Known gaps, where one exists.
10. Close on the loop's evidence block, then what was declined and where it went.
11. Given a path under `{docs_root}/specs/` as target, or the user saying the target is a spec, the skill reviews that spec and not the working tree. Any other path is code. Given no target, it reviews the working tree as before. [`pdlc-feature`](pdlc-feature.md) launches the review of a spec with the spec's path as an explicit target, and never relies on a default.
12. A path that does not exist, or a file that is not a spec, gives a stated error and nothing runs. "The spec" with no match, or several, asks for a path. A range holding both code and spec changes asks which to review.
13. A spec target is read by two fresh agents, one as business analyst and one as tech lead. Each is given only the spec path and the instructions of its own lens.
14. Each agent reports findings that are graded, numbered and one line each, tagged with its lens and its kind: a wording fix, an open question, or another kind.
15. A business analyst finding cites no code, no ADR and no architecture.
16. The tech lead reports whether the functional behavior can be built in the solution as it stands, or needs a structural change, and names the structure that would change. For a spec that names no existing structure, it says so.
17. The skill reports the two lists one after the other, numbered on across both, each finding kept as returned. A finding that cites the same place in the spec as another carries "same place as N".
18. No finding from either agent is missing from the report, regraded, reworded or merged into another.
19. The report names the sources each lens lacks, such as an empty `adr/` for the tech lead, and says that the conventions and libraries axes were skipped.
20. A spec with no Behavior section, or one that is empty or unnumbered, is reported as such by whichever lens sees it, and no lines are written for it.
21. A difference from `PRODUCT.md`, another spec or the code that the spec announces as a change is not a finding.
22. A lens that fails is reported as failed, the review is not presented as done, and a rerun of that lens is offered. A lens that returns nothing is reported as "no findings", naming the lens and the sources it read.
23. The skill asks which findings to apply and edits nothing before the answer.
24. A selected wording fix is applied to the spec. A selected open question is put to the user, and the answer is then written into the spec as a decision, with the rejected options if the user gave them. A selected finding of another kind states where it is referred, such as `pdlc-decide` for an ADR, and writes nothing. The review edits no file other than the reviewed spec.
25. A spec review reads no `build-loop.md`, runs no git or repository command and commits nothing. In the `pdlc-feature` flow the revised draft is committed at step 5, after the go-ahead on it.
26. A declined finding graded blocking or to fix, and an open question the user does not answer, are added to the spec's Known gaps with a condition the skill proposes and the user can correct. A declined detail leaves nothing.
27. Where the host cannot start agents, a session that wrote or discussed the spec says so and asks for a new session. A session with no memory of the spec reads it under both lenses in turn, and the report states that it was a single reader.
28. The review closes by stating what was applied, what went to Known gaps, and which open questions remain.
29. Where the two lenses diverge, the report shows both findings at equal weight. It prefers neither lens, marks neither as right and offers no tie-break.
30. The report states no verdict on the spec. A blocking finding does not stop the go-ahead, and the user can apply, decline or ignore any finding.

A review is not reportable as done while the target is unstated, the author's own reading presented as independent, the missing sources of truth unnamed, a library finding left ungrounded without being marked, or a correction applied outside the loop. A spec review is also not done while a lens is missing, a finding is dropped, reworded or merged, or an edit is made before the user selects it.

## Rejected alternatives

- **A step inside `build-loop.md`, before the commit ask** — the first shape considered, and rejected on two counts: it would run on every build whether or not the diff warrants it, and it would leave the review unreachable on any diff that did not come from a `pdlc-build`, which is most of them.
- **Relying on the host's generic review tooling** — rejected: it reviews a diff against general good practice, which is real value but not this one. It knows nothing of this repository's `AGENTS.md`, nothing of the spec that authorised the change, and nothing about which version of a library is installed — and those written sources are the whole reason this skill belongs in the kit.
- **Judging library use from the model's own knowledge of the API** — rejected, and it is the cheap version of decision 4: it reads identically to a grounded finding, it is wrong exactly on the libraries that moved between versions, and a review that confidently corrects working code into broken code costs more than no review at all.
- **Applying the obvious corrections first and showing the result** — rejected: a reviewer that edits before being asked is not a reviewer, and the user would be reading a diff they did not scope in order to find out what was done to it.
- **A hook or a blocking pre-commit gate** — rejected: `docs/PRODUCT.md` §5 closes that route outright, and it would be enforcement on a repository the product does not own.
- **Shipping a language-specific quality checklist with the skill** — rejected for the reason `pdlc-build` gives for not shipping a command table: every row would be an example borrowed from somewhere, and it goes stale silently against the repository it is supposed to serve.
- **Grouping findings by axis — spec, conventions, libraries, readability — instead of grading them** — rejected: the grouping tells the reader where a finding came from, and the decision in front of them is whether it matters enough to fix. Severity answers that question and the axis does not.
- **Recording every declined finding, details included** — rejected: it converts a review into a backlog and turns Known gaps into the noisiest section of every spec, which is how a section stops being read.
- **Writing the review itself into the spec as a record of what was inspected** — rejected: that is perishable state, true of one commit, and the same reason `pdlc-build`'s evidence block is session output rather than a spec section.
- **Granting the skill the repository's commands so it verifies its own edits** — the shape this spec was drafted around, and rejected during the build, which is why it carries evidence the others do not. Re-running the suite after an edit establishes that nothing broke; it does not establish that the correction did what it claimed, and a behavior-changing correction would have shipped with nothing behind it. What the implementation showed is that the permission was never the question — where the correction gets applied was. The code follows [ADR-0015](../adr/0015-review-corrections-enter-the-build-loop.md), and this skill ends up with no execution surface of its own at all.
- **Superseding ADR-0014 with the same list of the loop's callers plus this one** — rejected on the way to the above: the enumeration is the part that would keep needing a new record every time a skill reached the loop, which is a log entry that decides nothing.
- **`pdlc-feature` starting the spec review without asking** — rejected: it adds a step to every feature, including the trivial one, and decision 1 keeps the review on demand. A question the user can answer "no" to keeps the choice with them.
- **`pdlc-feature` never mentioning the spec review** — rejected: a review nobody is reminded of is rarely run, and the moment after the spec is written is when its findings cost least to act on.
- **A separate `pdlc-spec-review` skill** — rejected: it has the same invocation, the same fresh-agent rule and the same finding format. The rule would be stated in two skills and the copies would drift.
- **One agent wearing both lenses in turn** — rejected: the second lens is read through the first, which is the author's-reading problem again at a smaller scale.
- **Two agents with identical instructions** — rejected: they find the same points twice, for twice the reading.
- **An exchange between the lenses after the first round, where they disagree or the tech lead doubts the functional behavior can be built** — drafted, then removed. Two trial reviews on large specs found no disagreement of substance between the lenses, only differences of grade. The exchange needed triggers marked by fields nobody had specified, showed the analyst the tech lead's references to code, and produced rewordings that no lens re-checked. It is a known gap, to add when a review shows a disagreement it would have settled.
- **Letting both lenses read the code** — rejected: a business analyst who has read the code judges the spec by how the code works, and loses the user's view that the lens exists to give.
- **Giving the business analyst the original request** — rejected: the request lives in the conversation, and the conversation carries the author's reading. A spec that the build reads cold has to stand without it. The gap is recorded below.
- **The invoking session merging the two reports by judgement** — rejected: the merge is where softening could return, which decision 11 closes. Decision 15 shows the reports together instead.
- **Merging findings that concern the same point into one line** — rejected: deciding that two findings are one point is a judgement made by the session that relays them, and the merged line is a finding neither lens wrote.
- **Running a spec's corrections through the build loop** — rejected: a spec has no code to change and no test to fail, so the loop's steps would have nothing to assert.

## Known gaps

| Left out | Add it when |
|---|---|
| Nothing distinguishes an honest "this correction has nothing to assert" from a test written to have written one; the loop states the rule and cannot enforce it | A review is caught doing either — dressing a cosmetic correction in a test, or claiming a pass it did not make |
| A finding is a weaker loop input than a spec: it is durable only as long as the session, so a correction cannot be resumed the way a `Draft` spec can | A review is interrupted mid-application often enough that the selected findings need somewhere to live |
| Nothing calibrates the grades; "blocking" is the agent's own judgement, with no stated test behind it | A review is caught grading a detail as blocking, or waving through something that should have stopped a commit, often enough that a test would help |
| A library whose documentation is neither in the tree nor reachable leaves its axis unverifiable, and the review can only say so | That case is common enough on a stack actually worked on that a stated fallback beats repeating "unverified" |
| Nothing checks that the installed version is the one the running code resolves to, so a lockfile disagreeing with what is installed misleads the review | A review is misled by that gap rather than by an ordinary mistake |
| No rule for a diff too large to review in one pass | A review is run on a diff where the finding list stops being actionable, and the skill needs to say so rather than truncate silently |
| Nothing checks that the agent was started without the build's context, or that the relay passed its findings on unchanged; both hold by instruction | A review is caught carrying the build's reasoning, or dropping a finding between the agent and the user |
| A fresh agent re-reads the repository from nothing, so each review pays for that again | The cost is felt on a diff where the reading is short |
| A host with no way to start an agent leaves the user to open a new session by hand | That is the case on a host actually used, and a better route exists |
| A finding that contradicts `AGENTS.md` itself — a convention the code has collectively outgrown — has no route | That case occurs, and the referral to [`pdlc-decide`](pdlc-decide.md) is worth stating rather than leaving the review to argue with the document |
| Declined findings go unrecorded whenever no spec governs the diff, which is the common standalone case | A place to put them exists that is not a spec, and is not a backlog the kit would then have to own |
| The business analyst cannot check that a spec covers what was requested, because it never sees the request | A reviewed spec is found to omit something the request stated, which the review could not see |
| A spec review reads the repository once per lens | The cost is felt on a short spec, where one reading would have been enough |
| Nothing keeps the lenses apart: the split holds by instruction, and both agents may return near-identical lists | Reviews are found where the two lists barely differ |
| The lenses never answer each other, so a point the tech lead finds unbuildable stays unreconciled with what the analyst finds essential, and the user carries that exchange | A review shows a disagreement of substance between the lenses that an exchange would have settled |
| Two lenses were tried on two large specs only, so the yield on a short spec is unknown | A short spec is reviewed and one lens finds nothing the other did not |
| Nothing checks a citation: a finding may cite a place it does not concern, and the "same place" mark depends on it | A review is found with marks that link unrelated findings or miss related ones |
